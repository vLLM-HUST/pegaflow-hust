# 从端点等待与缓存失效证据出发的迭代

2026-10-26。当前工作区已快进到远端 `main` 的 `2b4b802`。P 端未提交 patch 与未跟踪文件先备份，更新前后 patch 逐字节一致。原版与历史结果均保留。自动任务保持暂停。

## 为什么做这项修改

不是继续调恢复惩罚或按速率挑调度器。上一版高档 `git-multibranch:11` 在 ready 后 12.8934 秒才开始历史复制，复制服务约 0.9001 秒。P1 先被 `fix-code-vulnerability:11`、`fix-git:11` 占用；P1 释放后，缓存源 P0 仍在执行 `dna-insert:12`。这里有**两个端点共同可用**的约束，不能把整个等待叫 RDMA 拥塞，也不能把请求自己的 0.6686 秒规划费用当作全部原因。

这条请求的初始 D 前缀命令为 16640 token，实际 D 接受 5888。源码检查发现并行预测 `sequence_for` 在尚未提交 D 时用路由命令构造序列；预测不推进缓存保存和回收，执行侧却推进。这是一个可复现的预测模型缺项。实际 D 边界还会在 P 完成后重新选择，所以不能将上述差额全部归因于回收，或把总端点残差称为纯排队误差。

最小例子：主机池装下两个块，P 引用这两个块后保存更长输入，源实现按 512 逻辑块的回收批次释放旧块。旧预测仍为随后 D 报价这两个块；新预测能看到首块已不可见，改按重算计费。512 来自现有执行模型，未按实验收益调节。

## 新候选与数学关系

`cache-evolving-batch-01` 继承 `bounded-proof-memo-02` 的候选顺序、64 项预算、pending-first 尾部目标、严格下界和同决策记忆化。执行世界不变，新的只是路由/恢复边界使用的预测。

令 \(L_j\) 是预测事件后的物理库存，\(H_j\) 是按请求和操作拥有的租约。对尚未启动阶段：

\[
\hat k=\min\{k^{cmd},\max(\operatorname{prefix}(L_j,d),\operatorname{prefix}(L_j,s))\}.
\]

若必须复制但完整包或暂存容量不可行，按实际回退契约取

\[
\hat k\leftarrow\min(\hat k,\operatorname{prefix}(L_j,d)).
\]

计算服务使用 \(C_d(N,\hat k B)\)，不是原命令 \(k^{cmd}\)。复制提交、完整 API 结束与同步保存后才更新

\[
(L_{j+1},H_{j+1})=\Phi(L_j,H_j,e_j).
\]

\(\Phi\) 保留实际共享物理 allocation 的唯一计费、租约引用计数、暂存可行性与源实现回收批次。已取得 API 的恢复边界和已完成 token 进度不能被新预测覆盖。未知生成内容占容量，但不能充当未来可复用前缀。完整 D decode 和保存继续占用资源；预测依然只包含当前已知请求，不读取后续请求或未来执行耗时。

这不是全局最优证明，也不是给真实 native 加了新功能。新增影子预测 CPU wall 与原规划、迁移、边界、批调度开销一起进入闭环 TTFT。

## 预先规定的检验

- 同一原始 95 请求、8 会话、三档名义 Poisson 流与 seed；不改变容量/成本/输出，也不按任务或速率特判。
- 先检查保存导致命中失效、容量失败保留本地前缀、共享租约最后释放三个直接相关契约，以及原日历检查。
- 比较上一候选和新候选的净 p99，另看 mean/p50/p95、原始首 token 预测残差、恢复/重算与端点等待。预测更详细不自动算成功。
- 首轮若三档都有潜力，反转候选/参考执行顺序确认；所有轮次保留，不选有利 reference。

## 结果与保留状态

首轮 `issue23-cache-evolution-01` 已 9 组 CPU 记账检查通过，全部 95 请求完成。暂定结果：

| rps | 同轮父版 p99(s) | 缓存演化候选 | 改善 |
|---:|---:|---:|---:|
| 0.2452 | 32.1170 | 29.2879 | 8.81% |
| 0.4903 | 34.6279 | 32.1107 | 7.27% |
| 0.9806 | 32.2762 | 28.4718 | 11.79% |

这不是全分布领先：低/高档均值与 p95 退化。路由加边界搜索 wall 从 57.42/81.47/63.60 秒增加到 125.35/125.70/127.11 秒。开销已计入上述 TTFT，不能再加一次，也不能扣掉制造收益。

原始 first 端点 MAE：低档 1.221→1.348、中档 1.371→1.376、高档 1.630→1.110 秒。并非全面改善。高档接受的 D 前缀总量 336768→203136 token，restore-path 总量 125.89→81.94 秒；这些是有重叠的聚合量，不可直接相加归因 p99。三档软件方向链路等待总量均为 0；这是本 CPU 场景的结果，不是实机 RDMA 未拥塞的证明。

首轮最慢请求均变为 `distribution-search:12`，原重点 `git-multibranch:11` 也不是每档变快。没有按某条请求特判，只调整了在线预测的物理状态约束。

首轮诊断导出发现已有 reserve 逻辑会把全部 effective-API 行的 request 改名为新请求。`source02` 将导出过滤为当前候选两阶段，保持决策与服务代码不变；首轮此字段不用于逐请求有效缓存统计，原档不改。反序确认使用 `source02`，其结果另列，不能混用。

反序确认 `issue23-cache-evolution-02` 也已完成并独立核验 9 组；source02 的 285 个原始预测都只含对应请求自己的两阶段，没有混入其他 live 请求：

| rps | 同轮父版 p99(s) | 缓存演化候选 | 改善 |
|---:|---:|---:|---:|
| 0.2452 | 29.4892 | 30.1492 | **退化 2.24%** |
| 0.4903 | 42.0268 | 29.4576 | 29.91% |
| 0.9806 | 33.1128 | 32.5734 | 1.63% |

反序三档 first 端点 MAE 分别为 1.415→1.128、2.141→1.300、1.456→1.166 秒，但低档 p99 仍变坏。该反证说明“预测平均更准”不是全局尾部优势的充分条件。实际计费的路由加边界 wall 是父版 65.25/93.09/94.68 秒、候选 111.39/134.14/117.19 秒；新增模型有真实的决策成本。反序中档父版从第一轮 34.63 变为 42.03 秒，也必须保留，不能只拿 29.91% 当稳定改善。

两个轮次的 native p99 几乎相同，而需要在线搜索的父版/候选会随实测控制 wall 改变交错、路由、恢复边界与后续会话 ready。CPU 工作者并行、执行顺序和操作系统计时仍可能参与这种变化，现有数据不能分离各自因果份额。这里没有新 NPU 干扰测量。

**保留结论：**缓存演化是已证实的模型缺项，新候选是有潜力的物理模型修正，尚不是稳定三档赢家；默认参考不替换。95 个开发请求的 nearest-rank p99 是最大值，不构成稳定显著性或真实并行硬件收益。下一项有依据的工作是剖析新增预测中重复的库存/lease/保存投影计算，优先做保持预测语义的复用；先测计算热点和同快照等价，再比较净 p99。不能为了保留此候选削弱容量/租约，或者按速率切换版本。
