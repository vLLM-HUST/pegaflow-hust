# 910B2 正常显存预算与三速率重跑（2026-10-26）

本次按用户要求移除每实例 2 GiB **设备 KV** 人工上限。它不是模型总显存；原实验的主机缓存池另有每实例 2 GiB 上限。本次只改变设备容量条件，主机池、95 请求/8 会话、三个速率、seed、模型、输出及代价种子保持不变。旧结果、失败候选和冻结 serving 源码都保留。

## 容量依据

设备为用户确认的 Ascend 910B2，64G HBM 档。官方 A2 硬件说明列出 64G 及系统占用；模拟优先用原 P 实测 `torch.npu.mem_get_info` 总量 **65,452,113,920 bytes（约 60.96 GiB）**，而非把名义显存全部算成 KV。系统预留已体现在框架可见总量中，不再重复扣除。

共享模型 `/data/shared_models/Qwen2.5-7B-Instruct/model.safetensors.index.json` 的实际权重大小为 **15,231,233,024 bytes**，约 14.19 GiB。BF16、TP1 的每 token KV：

\[
b_{KV}=2\cdot28\cdot4\cdot128\cdot2=57,344\ \mathrm{bytes/token}.
\]

CPU 容量情景使用：

\[
M_{KV}=B\left\lfloor\frac{\lfloor0.9 M_{visible}\rfloor-M_{weights}-M_{runtime}}{B}\right\rfloor,
\quad B=128\,b_{KV}.
\]

`M_runtime=4 GiB` 是显式的 activation/backend/workspace **未实测预留情景**，不是优化算法阈值或拟合时间惩罚。得到 **39,379,271,680 bytes = 36.6748 GiB KV/实例**。保留 2/4/8 GiB 运行时预留敏感性，不根据收益选容量。该范围下，设备 KV 均足以容纳四条完整 32K+128 token 序列的保守上界 **7.02734 GiB**，不会触发本模拟的容量准入阻塞。定向执行测试验证三个容量情景下四条完整序列的事件/首 token/完成时间完全相同；这不证明真实内核耗时与显存使用无关。

实机代码不写死上述估计容量：新副本设 `gpu_memory_utilization=0.9`，**省略 `kv_cache_memory_bytes`**，由引擎实测 non-KV 峰值再分配。当前本机镜像 CacheConfig 默认已经是 0.92，因此这里的 0.9 是明确固定的实验预算，不声称是所有版本的默认值。新 worker 保存实际 `num_gpu_blocks`；若未取得，记录证据缺失，不能把 CPU 估值写成实机结果。

容量来源、模型配置和 SHA 在 `experiments/issue23_strategies/memory/`。官方资料：
[dcmi_get_device_hbm_info](https://www.hiascend.com/doc_center/source/zh/HDK/2610/A2/A2DCMI/dcmi_050.html)。

## 同时修复的可复现预测错误

前一个 `recovery-deadline-01` CPU 矩阵的中档失败：真实模拟 D 已接受 prefix=0 并完成 8/9 token，预测却仍使用旧命令 prefix=1，再复制 8 个已完成 token，导致剩余 prefill=0、合并迭代时除零。不是模型输出错误，也不能用强制 `max(1, count)` 掩盖。

新预测对已经提交的序列使用**实际接受的 prefix 与已观察 token 进度**，包括等待内存准入的序列；服务成本仍用过去拟合，绝不复制执行世界未来成本。定向反例已从失败变为通过。此修复用于所有新比较组；不能把新旧差异全部归于容量或候选策略。失败的原完整档已保留，SHA `e8e7b33457712d1339da57780d83be9fa8dc0e873bdc4bb5f083f6b058eca7d6`。

## 高档退化的已观察机制

候选确实改变了策略：restore 延后 2117 次迭代；逐请求“等待其他请求 restore”的累计重叠量 19.41→4.25 秒（不是设备 wall 的可相加节省）。但全档 D restore 82.29→96.80 秒，compute 844.38→852.08 秒，路由+边界规划 wall 142.93→160.48 秒。迭代调度另收费 0.134→0.272 秒。这些区间在实际 TTFT 内，不能再叠加一次来算净收益。

对齐同一个最慢候选输入 `feal-differential-cryptanalysis:13`（24891 tokens）：

| 字段 | FairMemo | Deadline |
|---|---:|---:|
| TTFT 秒 | 18.4140 | 35.6478 |
| P / D | P1 / D0 | P1 / D1 |
| P 实际接受 prefix | 4096 | 4096 |
| D 实际接受 prefix | 0 | 4096 |
| P API 秒 | 10.1021 | 10.1021 |
| D API→首 token 秒 | 3.5791 | 19.3984 |
| 请求参与的 compute 区间秒 | 3.4644 | 17.6329 |

可见同输入、多恢复并不一定更快：目的节点及整条服务路径不同。参与 compute 的区间可能也含其他 batch 成员与同步保存，不是独占 FLOPs 时间。两组 D 数量分布 57/38 与 58/37 几乎相同，但具体输入的分配不同；强制数量均衡不能解决这种异质性。未记录所有未选路径的真实完成反事实，所以这张表不是单一排序改变的因果消融。

高档原 dispatch 预测 D1 full-end MAE 为 FairMemo 10.58、候选 11.06 秒，bias 均主要低估；first-endpoint MAE 1.80/1.96 秒。完整释放的误差明显大于首 token，值得继续核对后续到达与批成员变化造成的 decode 竞争，而非只给 H2D 加系数。原预测不能预知尚未到达请求，不能把这部分误差全部叫队列 bug。

所有 reference/candidate 的实际“持设备 gate 等方向锁”累计为 0；本轮仍没有支持 RDMA 带宽拥塞主导的证据。CPU 使用旧隔离成本与同一批处理近似，目的节点差异和大收益都仍需实机校正。

后续取向：保持正常显存预算，保留本候选失败原因，重点改进完整 decode/释放竞争的可解释预测与决策开销；不为了三档全赢切换不同算法或调整容量。未来实机自动分配要核每节点各 arm 实际 block 数相同，新的 staged audit 已加入该约束，缺 profile 或容量不一致不能通过。

正式运行前仍须实测新的可用块数、并行服务代价及初态；当前定时任务保持暂停。
