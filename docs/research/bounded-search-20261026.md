# 保留候选与有界搜索迭代，2026-10-26

本轮只使用 81 的 CPU，不启动 NPU 服务，定时任务保持暂停。输入、三速率、910B2 容量、D maxseq=4、完整 decode、H2D、同步保存、资源 gate 与过去信息约束均沿用 [当前对照协议](paper-baselines-20261026.md)。新版本独立冻结，未覆盖旧源码归档或结果。

## 从哪一个具体问题出发

当前 `TimedMemoSimulation` 的资源日历选择有降低尾部阻塞的潜力，但每组 95 请求的路由与边界计算约占 121–134 秒。上一次 `service-portfolio` 降到约 10–11 秒，却在三档均退化：只保留局部服务成本最小的代表，会丢失竞争情况下更合适的方案。该失败候选保留，不采用按速率切换版本或强制均衡配额。

本轮先优化**求解成本**，不删去原候选集、不改变 H2D/计算/复制估计、不增加收益权重。

## 两步迭代与可解释的界

候选 01 `bounded-calendar` 在每个冻结预测快照内，保留原始候选顺序、64 项工作预算和全部平局规则。设尚未输出首 token 的集合为 \(U\)，日历已推进到事件时刻 \(t\)。已在该预测中得到首 token 的请求使用其预测值；其余请求的首 token 不可能早于当前事件：

\[
\ell_r(t)=
\begin{cases}
\widehat F_r-a_r^{ready},&\widehat F_r\text{ 已由预测事件得到},\\
t-a_r^{ready},&\text{否则}.
\end{cases}
\]

\[
L(t)=\left(Q_{.99}(\{\ell_r(t)\}),\operatorname{sort}_{\downarrow}\{\ell_r(t)\}\right).
\]

各分量都是当前候选最终预测延迟的下界，排序和分位数保持此关系。只有 \(L(t)\) **严格劣于**已完整评价候选的前两项目标时，才停止本次预测。相等继续计算 full-release、P-release、字节等平局项。已经输出首 token 的 decode 仍保留在资源时间线，但不再进入可改变的 first-token 目标。

这不是此前已失败的“把聚合服务成本相加作下界”。它只使用同一个事件日历已经走到的时间，不额外假定 H2D/compute 可重叠或互斥。保证范围是**这个冻结预测模型和原预算内的选择**，不是全局最优，更不是对真实设备尾延迟的数学保证。

完整机制回放发现候选 01 在三档有 5577/6848/6217 次提前终止，其中部分是同一等价工作链重复被证明劣于最优值。因此候选 02 `bounded-proof-memo` 进一步保存**本次决策内的排除证明**：同一工作链、边界、成本与进度下，只有当前 incumbent 不劣于当时 incumbent 时，才复用证明。新请求、成本版本或进度快照不复用旧证明。没有把未完成预测当完整结果缓存。

### 高档退化的逐请求证据

候选02最慢请求为 `git-multibranch:11`，常规 TTFT 35.0838 秒；同一个输入在原版为 31.6221 秒。差值 3.4618 秒可严格对账为：

- P 开始前的控制/等待增加 **11.9968 秒**；
- P API 少 **2.7018 秒**；
- P 完成至 D API 多 **0.0324 秒**；
- D API 至首 token 少 **5.8655 秒**。

候选从 P0/D0 改为 P1/D1，接受的 P/D 前缀由 640/0 变为 6784/5888。请求自己的规划 wall 反而由 1.2860 降到 0.6686 秒；历史复制在 ready 后约 12.8934 秒才开始，复制服务约 0.9001 秒。因此不能把这条尾部退化归咎于“规划更慢”或“RDMA 链路服务更慢”。更多复用和更少 D 首 token 工作，仍没有抵消 P 开始前的等待。

原始路由 first 预测 367.4775，实际 first 380.0188，误差约 12.5413 秒；P end 预测误差约 2.9974 秒。初始 D 前缀命令为 16640，实际接受 5888，但**当前结果没有导出全部 effective shadow 前缀与 gate acquire 子事件**，不能用初始命令冒充预测实际接受量，也不能把这个误差全叫 H2D 或纯排队误差。下一步需区分原 route 的有效恢复预测、P 后边界修订和源端 gate 等待，不以统一恢复惩罚系数修补。

高档 63/95 请求更快，P/D 路由分别有 32/39 条改变，D 实际接受边界有 41 条改变；总分发 44/51 与 57/38，并没有极端单节点集中。总 restore 增加而 compute 区间减少，只是全局聚合现象，不能和关键路径等待相加来解释 p99。详见逐请求 [行为对账](evidence/bounded-search-20261026/behavior-09.json)。
