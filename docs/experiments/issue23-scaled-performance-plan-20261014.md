# Issue #23：共享传输瓶颈下的多请求测量方案

本方案基于已归档的四组运行和 2026-10-14 对 81、91 的只读核查。
后续实际执行与条件调整见 [八请求运行结果](issue23-eight-request-results-20261014.md) 和 [十六请求竞争实验](issue23-contention-pilot-20261015.md)；本文件保留当时的计划参数。
下列请求规模、带宽档位与实现均为下一轮计划；本次没有启动模型或更改网卡。

## 研究目标与具体主条件

研究对象为 P/D 分离、两节点共同提供 CPU 缓存时，命中远端缓存后的访问
代价：集中释放是否在共享传输容量上形成争用与排队，扩大缓存访问尾延迟，
以及这些延迟如何传导到新请求 TTFT 和已有解码请求 TPOT/ITL。
命中率、驻留、源状态和缓存字节数在本轮配对对照中保持一致。

正式主条件建议如下，所有数值须在实现后作容量和限速资格校准：

| 参数 | 主条件 |
|---|---|
| 四组 | RDMA集中、RDMA平滑、本地拷贝集中、本地拷贝平滑 |
| 前景请求 | 每组 1,024 条；四组共 4,096 次逻辑请求执行 |
| 配对 block | 每组 8 个，每 block 32 个 cohort |
| 每 cohort | 4 条完整混合缓存，包含全部 storage group 与两 TP rank |
| 每 cohort 缓存 | 当前 4K checkpoint 合计 593,100,800 字节 |
| 输入/复用 | 4097/4096 token |
| 前景输出 | 机制主条件 1 token，观察已有解码的 TPOT；端到端条件另用 64 token |
| RDMA 共享服务额度 | 先以 1 Gb/s 为主条件，按实测完成吞吐校准 |
| 平滑释放 | 四条分别在 Tg+0、1.2、2.4、3.6 秒获得提交资格 |
| 集中释放 | 四条均在 Tg+1.8 秒获得提交资格，平均释放偏移相同 |
| cohort 客户端到达 | 同批四请求同时到达，下一批计划在 20 秒后到达 |
| 已有解码 | 每 arm/block 保持 4 条，不占用更多前景运行槽位 |

Tg 为同一 cohort 四个完整 bundle 全部 eligible 的时刻。20 秒是主条件的
起始到达周期，独立于上一批完成；资格校准若显示不能排空或稳定处理，应
在正式运行前统一修改并冻结到达 trace。计划与实际到达、排队及违约全部
保留，不能把慢 arm 自动改为按完成时间发送。

解码背景使用短固定 prompt、足够覆盖 block 的输出预算，block 结束时
排空或取消并等待清理。若每 arm/block 启动四条，共额外 128 条背景请求。
4,096 的主计数不含源准备、捕获和功能资格请求；P、D 两阶段仍属于一次
逻辑前景请求。源准备次数与耗时单独记录。

主条件扩大瞬时争用的持续时间；可另设同一 1 Gb/s 共享瓶颈、额外 host-only
RDMA 背景到达 0.5 Gb/s 的条件，以产生持续竞争，不消耗 NPU 请求槽位。
每批 20 秒的前景平均缓存到达约 0.237 Gb/s，两者合计约 0.737 Gb/s。
在假定前景可用余量约 0.5 Gb/s 的算例中，单请求服务约 2.37 秒，平滑间隔
起始改为 2.4 秒，集中偏移 3.6 秒；实际公平份额须测量，不能假定背景
流自动获得固定份额。该额外条件完整跑四组时再增加 4,096 条前景执行。

带宽和间隔共同缩放：在无额外网络背景条件下，0.5、1、2 Gb/s 可分别以
2.4、1.2、0.6 秒为平滑间隔起点，集中偏移均为间隔的 1.5 倍。主条件先
固定一个档位完成大量配对请求，再执行独立冻结的敏感性条件。

该方案先确认“争用/排队→远端访问尾延迟→TTFT/已有解码影响”的机制。
随后另一个完整四组端到端条件恢复 64-token 输出，重新按处理能力冻结
cohort 周期；运行它再增加 4,096 条前景执行。

## 正式测量与运行效率

正式对照保留 RDMA集中、RDMA平滑、本地拷贝集中、本地拷贝平滑四组。
每个环境条件建议完整回放 1,024 条前景请求/arm，共 4,096 条。
分为 8 个配对 block，每个 block 含 32 个四请求 cohort，即 128 条/arm。
这是冻结的起始采样预算；按 block 报告效应与区间，p99 另报尾部样本与不确定性。
共用模型批次的请求和 token 间隔具有相关性，不能当作独立重复。
[分块实验](https://www.itl.nist.gov/div898/handbook/pri/section3/pri332.htm)、
[分层性能测量](https://kar.kent.ac.uk/33611/45/p63-kaliber.pdf)

每个 block 的四组使用相同用例、缓存状态、背景负载和到达 trace；arm 顺序
采用已有方案的平衡顺序并随机化，请求 slot 和数据集位置也要置换。
正式结果包括整份冻结清单，失败、时序偏差、超时和实际完成数量单列。

上一轮每 arm 总耗时约 247–310 秒，测量仅约 26–29 秒，测量占比约 9–12%。
最优先实现模型/engine 常驻、动态配置 arm 与 trial 身份、缓存按容量回收。
每个 trial 的前景清理必须等到其 CQ、H2D、lease 和请求全部结束；仅回收
对应前景身份。全局清理在 block 背景启动前完成；背景仍运行时不能清空其
缓存。真实 cache miss、完整四组状态和已复用 token 数继续验证。
同一份冻结源可以支持配对恢复测量；端到端测量仍须使 P 端实际计算和缓存
历史在四组间一致，并保留实际冷 prefill 时间。

每次仅准备一个四请求 cohort 或容量预算允许的少数 cohort，测完后回收。
每请求约 148 MB，1,024 个独立源约 152 GB，不能一次塞入当前 4 GiB host pool。
容量有界的回放可累计大量样本，无需同时驻留全部请求。

主测量记录 request/epoch/rank、关键事件、真实完成、错误、字节数及低频
cgroup 资源；大清单保存一次并引用 hash。H2D 描述符构建、API 返回、设备
完成、同步等待、通知分别计时。详细 trace 和 npu-smi 放在诊断重复中。
完成监测逐 bundle 并发进行，统一提交 worker；记录 gate 释放、实际 WQE
提交及 CQ 完成，避免把任务入队或顺序 await 的观察时刻作为物理完成。

## 并发、突发与持续负载

当前 `max_num_seqs=8` 是运行配置，不是已测出的硬件极限。4 条已有 decode
加 4 条新请求可以维持现有配置；更高并发需实际检查 HBM、cache 占用和
计算吞吐。总测量请求数与同时运行请求数是两个独立参数。

实际缓存量为每请求 148,275,200 字节，每四请求 cohort 593,100,800 字节，
包含两个 TP rank 与完整混合缓存。81、91 的 mlx5_2 端口均报告 100 Gb/sec。
以下为仅计 payload 的理想串行化时间，未含协议、内存、排队及 H2D：

| payload 服务带宽 | 单请求（ms） | 四请求总量（ms） |
|---|---:|---:|
| 100 Gb/s | 11.86 | 47.45 |
| 50 Gb/s | 23.72 | 94.90 |
| 25 Gb/s | 47.45 | 189.79 |
| 10 Gb/s | 118.62 | 474.48 |
| 5 Gb/s | 237.24 | 948.96 |
| 1 Gb/s | 1186.20 | 4744.81 |

单请求在理想 100 Gb/s 下也需要约 12 ms，与原 10 ms 提交间隔接近。
四请求可以形成短暂争用；是否到达链路能力需测量真实 WQE/CQ 与端口字节。
按原每 8 秒一个 cohort 计算，长期 payload 到达仅约 0.593 Gb/s；增加这种
间隔的重复次数能提高统计精度，却不会自动形成持续网络饱和。

用 S 表示平均缓存字节/请求，λ 表示实际外部缓存恢复到达率，R 表示可用
payload 带宽（bit/s），两个压力指标为：

- 长期负载比例：ρ = 8λS/R。
- 单请求服务时间与释放间隔之比：q = (8S/R)/Δ，本轮 Δ=10 ms。

若有生产的 ρ 或 q，可按这些比例确定缩小实验的带宽，而非只照搬标称端口
速率。还需生产的 payload 分布、缓存命中率、共享租户/节点、H2D 与解码
能力；相同 ρ 不会自动复现大规模的流数量、拥塞控制和设备内存干扰。

当前 payload 下，100 Gb/s 的理想持续饱和要求约 84.3 次恢复/秒。
举例，若后续实测稳态为 0.4 请求/秒，缓存到达约 0.474 Gb/s；要达到
ρ=0.6 的服务额度约为 0.791 Gb/s。0.4 是算例，不是当前系统的已验收容量。
25/10 Gb/s 更适合突发传输时间的敏感性研究，不能称为已模拟持续饱和。

以秒级的受限共享传输服务为主条件，保留原速作为容量及资格参考。生产
匹配值需要作者或运维的部署 trace。保留全部档位，独立冻结确认条件；
按单请求服务时间设置释放间隔，观察排队持续时间、尾部放大和等待代价。

## 可行的限速路径

当前两节点只读核查均显示：mlx5_2 为 PF 视图，`sriov_numvfs=0`，没有分配
专用 VF 的证据；`/sys` 只读，进程没有 CAP_NET_ADMIN/CAP_SYS_ADMIN。
现有 RC transfer backend 没有带宽配置，使用 `TransferOp::Read`。

**硬件额度优先。** 由平台提供专用 VF/vport 或可隔离的交换机 QoS，并确认
限速实际覆盖 RoCE payload。NVIDIA 文档提供 VF 和 VF group 的 TX 限速。
本实验 D 发起 READ、主要缓存数据 P→D，须检查 P 的响应发送方向及共享
端口映射；只限 D 的小 READ 请求包不等于限制缓存数据。
[NVIDIA SR-IOV 与 VF 限速](https://networking-docs.nvidia.com/doca/archive/2-10-0/sr-iov)

**软件注入额度可自主实现。** 在 RDMA backend 提交层按字节分块，使用跨
全部 QP/rank 共享的额度和在途字节上限；分别记录上层 eligibility、限速
队列等待、实际 WQE 提交和完整 CQ 完成。burst/smooth 共用相同的下层额度。
调度时继续轮询在途 CQ，避免限速等待阻断完成回收；buffer 保持至真完成。
初步可选不大于 1 MiB 的 chunk，具体精度由校准决定，token bucket burst
容量须明确，不能一次允许整个 148 MB bundle。

该方式控制注入吞吐，chunk 在物理链路上仍可能短时按原速传输，因此须
标记为软件 pacing 研究，不直接等同低速网卡或完整生产网络。应校准多个
消息大小、并发 QP 及不同时间窗口内的实际完成字节，报告 CPU 成本。

测量分别保留 policy release 等待、共享额度队列等待、WQE 提交到 CQ
完成、对象 eligible 到完整可用的访问时间。软件额度上的排队属于缩放的
共享传输服务模型；真实 RNIC/交换机拥塞需要硬件瓶颈，或让受控的独立
RDMA 背景流竞争原速链路，并实际验证前景吞吐和尾延迟变化。host-only
背景可以复用注册内存与多个 QP，无需为每个流启动模型；需记录其 CPU、
内存与 RNIC 干扰。硬件流控证据可包含 ECN/CNP/PFC 或交换机队列指标，
权限不可见时应标注。仅观察人工延时不能确立网络拥塞。
[DCQCN 研究](https://www.microsoft.com/en-us/research/?p=168656)、
[RNIC 资源与隔离](https://www.usenix.org/conference/nsdi23/presentation/kong)

普通软件 tc/qdisc 不能直接假定可限制硬件 RoCE；官方文档说明它绕过
Ethernet driver，需使用 RDMA 端口计数器。常见 verbs packet pacing 文档
针对 Raw Ethernet，不能直接套用当前 RC READ。perftest 的 SW limiter 可
帮助验证注入额度，但不修改 PegaFlow 或全机带宽。
[RoCE 路径与计数器](https://networking-docs.nvidia.com/mlnxofedswum/23040533/rdma-over-converged-ethernet-roce)、
[Packet pacing](https://networking-docs.nvidia.com/mlnxofedswum/24100700/programming)、
[perftest 参数实现](https://github.com/linux-rdma/perftest/blob/master/src/perftest_parameters.c)

每个网络条件完整保留四组；本地拷贝作为相同模型条件的路径对照，记录
网络额度对其不直接生效。网络条件与 burst/smooth 因素分别解释。

## 用例、指标与执行预算

本地已下载 MMLU-Pro test 12,032 条、validation 70 条，以及当前
FrontierScience olympiad 文件 100 条。正式清单建议按 MMLU 类别分层选
924 条，加全部这 100 条 FrontierScience，共 1,024 个不同用例；选择 seed、
版本、tokenizer、生成配置和清单 hash 在测量前冻结。全量指该冻结工作负载
的完整回放；若选择原始 MMLU 全 test，也可以按同样的容量有界方式完成。

以固定 4097 输入、4096 复用、1 个 prompt 尾 token 运行大规模
主对照，前景 1-token 机制条件与 64-token 端到端条件分别报告。使用题干完整的可审计上下文
扩展并标记为控制长度用例。随后独立测自然长度和预先固定的 8K payload；
不能把人为 padding 的长度分布当生产分布。8K 档四组统一 context/runtime。

固定背景 4 条，短 prompt、固定 seed，达到预先规定的已生成 token 数后
启动同一份 cohort 到达 trace；预算应覆盖整个 block。记录每次注入时的
实际生成 token 数及背景活跃数量。端到端稳态验证采用开放到达 trace，
记录计划与实际发送时刻、积压、拒绝和超时。
开放到达可参考 MLPerf Server 的原则。
[MLPerf Inference rules](https://github.com/mlcommons/inference_policies/blob/master/inference_rules.adoc)

同报远端缓存访问与实际 RDMA 完成时间的 p50/p95/p99、新请求 TTFT（含
人工等齐及 policy 等待）、各等待分量、D 端 gate→首 token、真实 RDMA/CPU
copy、H2D、背景 ITL/TPOT、吞吐与失败率。优先用传输阶段指标检验机制，
再判断端到端传导；不能因端到端方差大而遗漏传输效应。TTFT 直接依赖缓存
恢复完成；已有 decode 的 TPOT 恶化则需资源干扰、阻塞或 decode 中额外
访问的实际证据。若已有 decode 平稳，需如实报告这种结果。

请求较多并不意味着所有环境都要一次展开。先完成共享瓶颈方法和时序的
资格校准，再执行受限带宽下的千条级四组主对照，保留原速参考。
完整部署的启动检查只作功能资格；正式结论来自多请求运行。

主条件每组 256 个 cohort，20 秒的冻结周期使四组测量窗口合计约 5.7 小时，
另加源准备、排空和背景重建。该估计来自预定 trace，不是已测 ETA；资格
校准后若变更周期，预算同步重算。64-token 条件需重新标定持续完成能力。
提高效率主要来自启动摊销、缓存准备复用和低负担测量，不能以丢弃失败
或跳过完整状态恢复换取吞吐。

实施顺序：常驻服务与安全 epoch → 完成/H2D 测量修正 → 冻结多请求清单
及可恢复 runner → 共享传输瓶颈与可配置间隔资格 → 秒级争用的正式四组
→ 持续网络背景与完整输出条件。
