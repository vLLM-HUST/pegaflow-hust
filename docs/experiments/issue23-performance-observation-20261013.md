## 性能样本的有效性

采样前进行短的语义检查，并保存可复核证据：

1. 输入与模型身份：相同输入 token、模型 revision、布局、TP rank、前缀 hash 和
   恢复边界；前缀分叉与模型身份不匹配时，正确拒绝命中或回退。
2. 完整状态：目标端实际恢复所需 attention K/V 与全部 conv/SSM；按 rank、层和
   边界核对来源与字节覆盖，排除错槽、越界、残留数据及不相容状态组合。
3. 真实复用：记录命中长度、实际执行的 prefill tokens 和传输字节。缓存命中与
   回退重算分别统计，不能把完成 HTTP 请求当作复用成功。
4. 生命周期：请求完成、取消或失败后，ACK、引用、lease 与传输计数能够收敛。
5. 各臂可比：同一请求在对照臂中使用相同 token、恢复边界、状态集合和传输量。
   如果某臂多做了 prefill 或少传 recurrent 状态，单独记录为路径差异。

这些检查通过的配置可进入性能观察。输出差异保留为独立字段；出现明确的错误
状态、缓存身份错误、漏传或生命周期问题时，该组样本不能支持优化结论。
现有历史报告的严格输出检查结果保持原样，本文件规定后续性能样本的判定口径。

## 采样路径与指标

计时使用原始模型计算路径、SCHED_OTHER/nice=0。关闭张量转存、逐层 checksum
及 logits 探针，关闭为数值归因增加的投影补零；语义检查与性能采样分别运行。

首轮固定单一生产历史和新实验命名空间，先确认完整缓存恢复的性能：冷计算、
本地缓存复用、跨节点缓存复用。固定输入及输出 token 数，并检查提前结束、错误
和超时，避免输出长度变化影响延迟比较。

随后进行 #23 的 RDMA/本地拷贝 × smooth/burst 四臂对照。现有冻结计划只接受
`k`/`v` segment；完整混合缓存实验开始前，需要核对 recurrent fetch 是否完整
关联到同一请求及 cohort 门控，明确全部字节是否受到相同调度处理。

记录客户端 TTFT p50/p95/p99、完整请求延迟、吞吐、传输完成时间、门控等待、
实际提交偏移、成功/错误/超时数量，以及每请求恢复/重算 token 数。使用固定到达
轨迹，多轮交替臂次序。先报告样本数和分布，再判断差异；小样本 p99 作为探索性
观察，不能据此直接推广稳定的尾延迟收益。
