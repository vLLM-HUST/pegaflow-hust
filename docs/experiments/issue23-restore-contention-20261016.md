# Qwen2.5 2P2D：恢复路径与 CPU RDMA 竞争续测

2026-10-16，基于已合并的 [PR #38](https://github.com/vLLM-HUST/pegaflow-hust/pull/38)。本轮新增 570 条测量请求，540 条成功；30 条超时均出现在 NUMA 绑定配置的高负载组。前景测量累计 12.9 分钟，模型加载、标定、服务切换和归档另计。

## 结论

CPU RDMA 竞争使前景 fetch p95 从 138.24 ms 增至 356.64 ms，停止竞争后回到 136.25 ms，约为竞争前的 2.58 倍。与此同时，TTFT p95 为 3.26→3.44→26.98 s；后控的异常主要发生在 D1 的 CPU→NPU 恢复队列与后端调用/同步阶段，不能将三组端到端差异直接归因于网络竞争。

恢复完成观察通常为十几毫秒；现有证据将主要等待定位在恢复任务排队与后端执行。底层不稳定原因仍待定位。NUMA 本地绑定未消除问题，当前不能作为已验收的性能优化。

## 固定条件与处理

- 两物理节点各两张 910B2：81 的 P0/P1、91 的 D0/D1，每实例 TP1/PP1。
- Qwen2.5-7B-Instruct BF16，固定 95 条完整历史快照、seed=17、开环 Poisson 到达、随机 D 路由；D 固定生成 256 tokens。
- 每 P CPU 池 8 GiB、每 D CPU 池 16 GiB；每实例 NPU KV 预算 16 GiB，max_num_seqs=8；默认 OS 调度。
- 前景为正常 NPU→CPU→RDMA→CPU→NPU 路径，保持原速。
- NUMA 对照仅给 D engine 增加 numactl CPU/内存绑定：D0 的 CPU 0–23、memory node 0；D1 的 CPU 96–119、memory node 4。实际 16 GiB 大映射分别全部位于 N0/N4。中负载后进入高负载；30 条超时后保留数据并恢复未绑定配置。
- 网络三组在恢复未绑定配置、重新加载并预热之后运行；三组之间不重启模型/engine。只有中间一组启用独立注册 CPU 内存的 perftest RC READ 背景，4 QP、1 MiB payload、tx depth 32、outstanding READ 16。
- C₀ 复测 90.48 Gb/s。背景软件额度为 86 Gb/s，160 秒连续运行实测平均 83.61 Gb/s（92.4% C₀）。该数值是整段平均；1 Hz RNIC 样本为共享端点总流量，不能据此精确分离每秒前景/背景吞吐。
- 前景竞争组窗口 1792149810574498574–1792149934214227882 ns，位于背景数据阶段约 1792149780340777850–1792149940565556349 ns 内。后台结束后才运行后控。

## 测量结果

| 条件 | 请求率 /s | 成功 | TTFT p95 s | TPOT p95 ms | 成功请求 RDMA fetch p95 ms |
|---|---:|---:|---:|---:|---:|
| 未绑定，M | 1.249 | 95/95 | 3.983 | 23.21 | 122.45 |
| NUMA 本地绑定，M | 1.249 | 95/95 | 3.884 | 22.80 | 123.76 |
| NUMA 本地绑定，H | 1.616 | 65/95 | 110.778 | 76.88 | 124.07 |
| 无竞争，前控 | 0.735 | 95/95 | 3.263 | 20.01 | 138.24 |
| CPU RDMA 竞争 | 0.735 | 95/95 | 3.440 | 20.77 | 356.64 |

30 条超时保留在分母中；高负载延迟分位数只描述 65 条成功请求，不能代表全部 95 条的有限延迟分布。该点 95 条都完成了完整前缀发现；这不等于所有恢复和推理均成功完成。原计划的 NUMA 低负载点因高负载未通过而没有执行。

## 网络三组的分段证据

| 指标 | 前控无竞争 | CPU RDMA 竞争 | 后控无竞争 |
|---|---:|---:|---:|
| P API 均值 s | 0.825 | 0.824 | 0.823 |
| RDMA fetch 均值 ms | 59.89 | 167.59 | 59.66 |
| D 提交至首 token 均值 s | 0.549 | 0.629 | 4.205 |
| D1 恢复跨度均值 s | 0.367 | 0.330 | 7.249 |
| D1 恢复 worker 前等待均值 s | 0.033 | 0.027 | 6.116 |
| D1 后端 API 均值 s | 0.195 | 0.180 | 0.660 |
| D1 stream sync 均值 s | 0.130 | 0.115 | 0.464 |
| D1 完成观察均值 ms | 7.47 | 6.97 | 7.17 |
| D 平均 AI Core 活动 % | 77.6 | 77.5 | 65.8 |
| D 平均 CPU cores / 8 quota | 2.68 | 3.78 | 2.83 |

恢复阶段有包含关系，分位数不能相加。native 阶段按单 worker FIFO、块数和同主机时间戳关联；共享恢复分别归属其覆盖的请求。API 和同步跨度包含运行时与共享资源竞争，不能直接等同于设备 DMA 时间。NUMA 高负载存在未观察到完成的恢复批次，未匹配项保留在 restore.json。

D 端的 AI Core 采样峰值为 100%。正常低负载的活动水平约 77%；后控恢复排队时降至约 66%，NUMA 高负载含长等待与超时的完整窗口均值约 22%。这些是活动采样，不是理论 FLOPS 利用率。网络竞争组 CPU 使用增加约 1 core；配额节流仅 23.5 ms 左右，仍需区分网络和端点竞争。NUMA 中负载的 D 资源采样只有约 52/94 秒，未将其作为完整窗口均值用于对照。

## 记录与边界

- 数据、源代码 overlay、配置、perftest 输出、worker/native 遥测和客户端事件保存在共享目录 `/data/shared_upload/hust-zsx/issue23-restore-20261016`，并复制到本机实验结果目录。
- 运行时复用 0.23.4 原生制品及既有 Python 环境；本轮不重建 native。新工具位于后续工作分支 `feat/issue23-restore-diagnosis`。
- 初始化后台工具时有一次模式检查失败，前景竞争组尚未开始；其记录独立保留在 background/。正式竞争使用 background-finite/。
- 服务切换期间观察到 91 agent 重连；各点运行边界单独记录。清理阶段另行验证 81/91 的 NPU 均无运行进程。
- 单种子、各点 95 条请求，存在端点漂移；本轮未提供稳定 p99 或多物理源 fabric incast 的证明。数值输出一致性不是本轮性能验收项。
